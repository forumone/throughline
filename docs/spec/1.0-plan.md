# Throughline 1.0

Progress is tracked in [`docs/roadmap.md`](../roadmap.md#throughline-10), as checkboxes per phase. This file holds the reasoning: what 1.0 changes, why, and how forumone-2026 upgrades to it. Agreed 2026-10-01. Phase 0 was complete the same day.

The map from every 0.x import path to its 1.0 one is [`1.0-exports.md`](1.0-exports.md).

## Sequencing: add first, break once

Everything 1.0 adds ships first, as ordinary 0.x releases from `main`: the jobs interface, its adapters, and the code moving in from forumone-2026. forumone-2026 adopts each piece in production, one pull request at a time, and deletes its own copy. Only then does 1.0 break anything: the package consolidation, in pre-release mode, with a short-lived `v0` branch for 0.x fixes.

The reasons:

- **Each risky piece is proven in production on its own.** The job runner swap is the riskiest, because in-flight scheduled publishes depend on function ids. It lands on its own, not in the same PR as a package restructure.
- **The 1.0 API is frozen after real use, not before.** The jobs interface and the editorial views run on forumone.com before 1.0 commits to them.
- **The final migration is mechanical:** a package swap, the import codemod and one `throughline()` call.
- **`v0` lives for weeks, not months**, so little has to be ported between two diverging codebases.

**The rule, until pre-release mode starts:** nothing merged to `main` may break forumone-2026's current imports, plugin options or schema. 0.x semver would allow a minor release to break things; this plan doesn't. New code lives in an existing package for now, for example jobs in `workflows`, and media usage and the field kit in `core`. That avoids new npm names 1.0 would delete. The codemod moves the imports later.

## Where 0.x left things

- **Fourteen packages, shipped as twelve published plus config packages.** The plugins must load in a fixed order, and a capability registry checks that order at boot. They are one product cut into pieces, and every piece costs a changeset and a release.
- **Inngest is a peer dependency of seven packages,** so a second site has to adopt Inngest to use any of it. Across both repos there are 22 functions, using only `step.run` (60 calls), `step.sleepUntil` (3) and `step.sendEvent` (1). That keeps an abstraction over it small.
- **forumone-2026 consumes the suite as a git submodule**, pinning a commit. The pin once sat on a pre-squash branch commit that no release named, and only a feature branch held it. The site's `check-throughline-pin.sh` now stops that. A second client should still not inherit a submodule.
- **`@forumone/throughline-design-system-payload` is marked `private`** and has never been published. The site doesn't notice, because it consumes source, but a second site installing from npm would.
- **Some code serves a second site that does not exist yet:** the scaffolder (~6,700 lines), forms (~2,300, unused by the only consumer) and reference-ds (~2,800).

### Publishing on the minute under Payload Jobs

Measured in P1 against the playground's own config (`playgroundConfig`, SQLite in memory), with
`autoRun` on its every-minute cron and `getPayload({ config, cron: true })`. Two pages were
scheduled: one on the next minute boundary and one thirty seconds after it. Then the live row was
polled every 250ms. Two runs:

| Scheduled for | Run 1 | Run 2 |
| --- | --- | --- |
| A minute boundary | 0.22s late | 0.12s late |
| Mid-minute (:30) | 30.10s late | 30.19s late |

So a publish scheduled on the minute lands within a second, and anything else lands on the next
tick. Lateness is bounded by the tick interval (just under 60s), not by the job. The
`publish-at-scheduled-time` job's `sleepUntil` becomes a continuation queued with `waitUntil`, and
the next run picks it up. "On the minute" is the promise, so the boundary row is the one that
has to hold. That settles decision 3.

Three caveats:

- **`autoRun` only starts when Payload is booted with `cron: true`.** Payload 3.90 calls
  `_initializeCrons()` only then. `@payloadcms/next` passes it, so a dev server runs the queue; a
  bare `getPayload({ config })` in a script or test never does, and the first measurement saw
  nothing publish at all.
- **On Vercel the tick is Vercel's cron**, calling `/api/payload-jobs/run` every minute, not this
  in-process one. Its timing was not measured here. A preview test with a publish scheduled ten
  minutes out (P1's adoption step) covers that.
- **A schedule between minutes waits for the next tick** under Payload Jobs. Inngest's
  `step.sleepUntil` wakes at the time itself, so a site that needs better than a minute stays on
  Inngest.

Rules inside `@forumone/throughline`:

- **Workflows splits up by owner.** Revalidation and scheduled publishing go to `/publishing`, approval expiry to `/approvals`, audit fan-out to `/audit`, and the healthcheck to `/integrations`.
- **The plumbing becomes internal.** That means the capability registry, the `Symbol.for` accessors and the MCP tool collector. `throughline()` owns the registration order.
- **Heavy dependencies become optional peers.** `resend`, React Email and `inngest` load only through the subpath that needs them.
- **The root holds only what is shared:** configuration, `assertEnvironment`, access helpers and the logger.

## Distribution

- **Until forumone-2026 migrates (Phases 0–3):** it keeps the submodule. Its CI refuses a pin that is not on this repo's `main`. From P3 the check also accepts `v0`.
- **Fixes during P3:**
  - A 0.x fix goes to `v0`, and is ported to `main` by hand if 1.0 needs it too.
  - `release.yml` also runs on `v0`, and `v0`'s changesets config sets `baseBranch: "v0"`, so a merge there opens a 0.x release PR against `v0`.
  - 0.x stays on the `latest` dist-tag and pre-releases go to `next`. After 1.0 ships, a `v0` release needs its own dist-tag so it doesn't take over `latest`.
- **After the migration:**
  - The site depends on `@forumone/throughline@^1` from npm, and Renovate opens the bumps.
  - A pull request here publishes a snapshot (`<version>-pr-<n>.<sha>`, dist-tag `pr`), so a site PR can install the change before it merges.
  - Every merge to `main` publishes a `next` snapshot. Stable releases follow a cadence (weekly), or come on demand.
  - Developing both repos side by side: a `.pnpmfile.cjs` hook links a sibling checkout when `THROUGHLINE_LINK` is set, and the site's CI refuses any `link:` to Throughline in its lockfile.
- **What changes for a fix:** the pull-request count stays at two, one here and one in the site. The difference is that the site's `main` points at an immutable published version instead of a commit.

## The jobs interface

Every plugin writes its background work once, against `@forumone/throughline/jobs`.

- **`defineJob({ id, on, retries, onFailure }, handler)`**
  - `on` is an event name or `{ cron }`.
  - The handler gets `{ event, step, runId, logger }`, where `step` offers `run`, `sleepUntil` and `sendEvent`, and `event.ts` is the send time. No Payload instance: a job that needs one closes over it, as every factory already takes `payload` in its options (#211).
  - Idempotency is declared as `event.data` fields plus a separator, because Payload Jobs has no expression language. The Inngest adapter compiles it back to the exact CEL string a function was written with.
  - `emit(event, data)` sends an event. Event names keep today's taxonomy.
- **`inngestJobs(client)`** wraps `createFunction`. It keeps today's function ids, so runs in flight survive the upgrade. forumone-2026's Inngest environment pinning moves in here.
- **`payloadJobs()`** maps each job onto a Payload workflow:
  - `step.run` becomes an inline task.
  - `sleepUntil` re-queues the job with `waitUntil`.
  - An event queues one job per subscriber.
  - On Vercel it needs a per-minute cron hitting Payload's run endpoint; elsewhere it uses `autoRun`.
- **Failure handling lives in the adapter layer.** That means the `job-failures` writer and error reporting (#198).
- **Where it lives in 0.x:** `@forumone/throughline-workflows`, which already owns the Inngest functions. It moves to `@forumone/throughline/jobs` in P3.
- **Done when:**
  - every workflow test passes against both adapters;
  - the playground runs on `payloadJobs`;
  - forumone-2026 runs on `inngestJobs` **in production**, with its function ids unchanged.

## Migrating forumone-2026

By P4 the site already runs the 1.0 code: the jobs adapter since P1, the moved features since P2. What is left is the packaging. It is one site pull request, rehearsed during P3 on a `chore/throughline-next` branch that tracks each `1.0.0-next.N`. The aim is that no database table or column changes.

1. **Dependencies.**
    - Remove the submodule and its workspace entry.
    - Add `@forumone/throughline@1` and `@forumone/throughline-design-system@1`, then check with `pnpm install --frozen-lockfile`.
2. **Imports.** Run the shipped codemod, which rewrites the 57 import sites, then typecheck.
3. **`payload.config.ts`.** The plugin calls and the hand-built MCP collector become one `throughline({...})`. Jobs and the moved plugins are already registered from P1 and P2; only their import paths change.
4. **Jobs.** Nothing to do beyond imports: the site has run `inngestJobs` since P1. Confirm the function ids are unchanged.
5. **Moved code.** Already deleted in P2. Confirm nothing in the site still imports a 0.x temporary home.
6. **Schema.**
    - `migrate:create` should find nothing to change. Run it with a placeholder `BLOB_READ_WRITE_TOKEN` set, or the storage plugin's fields are missed.
    - A proposed change means a field name drifted: fix the option, don't migrate.
7. **Generated files.** Regenerate `payload-types.ts`, `importMap.js` and block options. `importMap.js` will change, because admin components now come from the package.
8. **Repo rules.**
    - Rewrite `CLAUDE.md`'s submodule section.
    - Retire `check:boundary`, `check-throughline-pin.sh` and the CI steps that ran this repo's tests.
    - Add the snapshot-install and `link:` gates.
9. **Verify.**
    - Run the full `fast` and `verify` gates, and diff `.next/prerender-manifest.json` against `main`.
    - Smoke-test the admin against a local Postgres: calendar, content health, "Used on", a scheduled publish, an approval link, and the `/api/mcp` tool list.
10. **Ship.**
    - Deploy a preview with a publish scheduled ten minutes out.
    - Merge, then promote.
    - Rollback is promoting the previous commit, which is safe only because step 6 produced no migration.

## Risks

| Risk | Containment |
| --- | --- |
| A changed function id orphans an in-flight scheduled publish | `inngestJobs` keeps ids; a preview test schedules a publish ten minutes out |
| A renamed field turns into a data migration | 1.0 defaults match the site's names; a `migrate:create` that changes nothing is the gate |
| The site migration becomes a big-bang PR | Add first, break once: the job runner and the moves reach production in P1 and P2, so P4 is packaging only. Rehearse it on `chore/throughline-next` during P3. |
| An "additive" 0.x release breaks the site | Until P3, nothing merged to `main` may break the site's imports, options or schema. Each P1/P2 change is adopted by the site in its own PR, so a break shows up at once. |
| A 0.x fix is needed during P3 | It goes to `v0` and is ported to `main` by hand if 1.0 needs it. P3 is kept short, because ports get harder once paths move. |
| The consolidation is deferred because 0.x feels good enough | The roadmap's P3 gate: 1.0 is not done until `1.0.0` is on npm and P4 has landed |
| Payload Jobs on a per-minute cron misses "on the minute" | Measured in the playground: on the minute it lands within a second (see below). The Vercel cron path is still unmeasured, and forumone-2026 stays on Inngest either way |
| Scope creep from site-specific code | Okta, HubSpot, Greenhouse, narration and preview stay out of 1.0 |
