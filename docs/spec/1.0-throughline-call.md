# `throughline()`: one call for the whole suite

Decision 5 in [the 1.0 plan](1.0-plan.md): one `throughline({...})` call registers the plugins in order and wires the MCP collector, and each plugin is still exported on its own. This is the proposal for that call, drawn up 2026-10-03 from how forumone-2026 wires the suite today, for review before any of it is built.

## What a site does today

forumone-2026's `plugins/throughline.ts`, `payload.config.ts` and `app/api/inngest/route.ts` between them:

- **Call eleven plugins in an order kept by comments.** `auditPlugin` first, because the rest `requireCapability('audit-log')` at init and refuse to load without it.
- **Thread one MCP collector through nine of them.** A plugin not given `mcpTools` loses its tools silently, which is why the site has a test (`mcp/collectedTools.test.ts`) counting them.
- **Hand an Inngest client to five,** so that each can send events.
- **Repeat the constants plugins must agree on.** The approvals collection's slug is given to `approvalsPlugin`, `emailPlugin` and `expireStaleApprovalsJob`. The third call site was missed, and the expiry job threw every night for eighteen days (the site's audit 12 H1). The content collections are given to publishing, editorial and both scheduling jobs.
- **Assemble the Inngest function list by hand.**
  - Six platform jobs, each with site options.
  - Email's functions, read off the Payload instance with `getEmailFunctions`.
  - Each integration's functions, read through `getIntegrationRegistry` and `getIntegrationContext`.
  - A `publishScheduled` function that every site writes identically, publishing through `getPublishingService`.

Every one of those is a thing the platform knows and the site has to restate.

## The call

```ts
// payload.config.ts
import { throughline } from '@forumone/throughline'
import { inngestJobs } from '@forumone/throughline/jobs/inngest'

export const suite = throughline({
  jobs: inngestJobs(inngest),                 // or payloadJobs(); see "Jobs"
  collections: CONTENT_COLLECTIONS,           // what publishing, editorial and scheduling govern
  admin: { group: 'Workflow' },               // default sidebar group for every collection it adds

  publishing: { seoField: SEO_GROUP, urls: revalidationUrlBuilders },
  approvals: { collectionSlug: 'approval-requests', groups, groupResolver },
  email: { resolveApprover, resolveRequester, tokens },
  integrations: { integrations: [hubspotIntegration, greenhouseIntegration], admin: { group: 'Admin' } },
  components: { manifest: { type: 'object', manifest }, matching: { strategy: 'tfidf' } },
  references: { collections: [{ slug: 'media', noun: 'file' }, /* … */] },
  editorial: { health: { checks }, calendar, palette },
  healthcheck: { checks: [createPayloadReachableCheck()], schedule: '0 * * * *' },
})

export default buildConfig({
  // …
  plugins: [
    suite.plugin,
    mcpPlugin({ mcp: { tools: suite.mcpTools }, overrideApiKeyCollection: mcpApiKeyAccess(isAdmin) }),
    // the site's own and Payload's official plugins
  ],
})
```

```ts
// app/api/inngest/route.ts
export const { GET, POST, PUT } = serve({
  client: inngest,
  functions: registrableInngestFunctions([
    ...inngestJobs(inngest, { onFailure, payload }).functions(suite.jobs),
    ...siteFunctions,
  ]),
})
```

### What it returns

| | |
| --- | --- |
| `plugin` | One Payload plugin that applies every enabled Throughline plugin in the right order. Order is no longer the site's problem. |
| `mcpTools` | The collector's tool array, for `mcpPlugin`. Every enabled plugin declares into it, so none can be left out. |
| `jobs` | Every platform job the options call for: revalidation, both scheduling jobs, approval expiry, the audit echo, the healthcheck, email's three notifications, and each integration's jobs. |

### What it decides for the site

- **Order.** Audit, then job failures, components, publishing, approvals, the audit query, email, integrations, references, fields, editorial. That's the order forumone-2026 uses now, and the capability registry's checks still run, so a mistake inside `throughline()` fails loudly.
- **One value for each shared constant.**
  - `approvals.collectionSlug` reaches approvals, email and the expiry job.
  - `collections` reaches publishing, editorial's "Your work" and both scheduling jobs.
  - `admin.group` is the default for every collection a plugin adds; a plugin's own `admin.group` overrides it.
- **Events.** Plugins that send events (audit, publishing, approvals, integrations) are given `eventSenderFor(jobs)` instead of an Inngest client. On Payload Jobs that means no Inngest at all, which is what decision 3 needs.
- **Scheduled publishing goes through the pipeline.** The `publish` callback every site writes is built in: it publishes through the publishing service as `scheduled-publish`. A site can still pass its own.
- **The terminal-failure handler** is `createTerminalFailureHandler({ payload })` unless one is given. It's the one the site passes today.

### Turning a plugin off

Audit, job failures and fields are always on: the rest depend on the first, and the other two cost a site nothing it doesn't use. Every other plugin is on when its key is present, so `email: {}` turns email on with its defaults, and leaving the key out leaves it off. A site states what it uses.

### Jobs

`jobs` is the adapter, used for two things: sending events at runtime, and on Payload Jobs, running the jobs.

- **On Payload Jobs,** `suite.plugin` registers `suite.jobs` with the adapter itself, so nothing else is needed.
- **On Inngest,** Inngest's endpoint is the site's, so the site serves `suite.jobs` through `inngestJobs(inngest, { onFailure, payload })`, as in the example. **Function ids don't change.** Each job keeps the id its `create…Function` factory had. The parity snapshots in `jobs/function-ids.test.ts` and email's and integrations' registration tests already pin that, and `suite.jobs` gets a test of its own.

## What becomes internal

| Public in 0.x | 1.0 |
| --- | --- |
| `getPluginRegistry`, `resolveAdminGroup`, `DEFAULT_ADMIN_GROUP`, `PluginRegistry*` | internal |
| `createMcpToolCollector`, `McpToolCollector` and its types, `toPayloadMcpTool(s)` | internal; `suite.mcpTools` replaces them |
| `getEmailFunctions`, `getIntegrationRegistry`, `getIntegrationContext` | internal; `suite.jobs` replaces what the route used them for |
| `getPublishingService` | **stays public**: it's the server-side publishing API for host code, not plumbing |

Each plugin stays exported from its subpath (decision 5), still taking `mcpTools?`. A site wiring plugins by hand gets a collector from the plugins' own options type until there is a reason to remove that path.

## What forumone-2026 changes in P4

- `plugins/throughline.ts` becomes the `throughline({...})` call. Its comments move to the options they explain.
- The collector in `payload.config.ts` goes; `mcpPlugin` takes `suite.mcpTools`.
- The Inngest route serves `suite.jobs` instead of six jobs and two accessor lookups. Its `publishScheduled` goes.
- `mcp/collectedTools.test.ts` stays: it asserts the served tool set, which is still worth asserting.
- **Expect no migration.** The same plugins register the same collections and fields, which the P4 gate (`migrate:create` finds nothing) checks.

## Open questions

1. **Should `throughline()` register `mcpPlugin` too?** That would remove the last ordering hazard (`mcpPlugin` reads the collector at `order: 10`), but it adds `@payloadcms/plugin-mcp` as a peer and puts a credential policy (the key collection's access) inside the platform. The proposal leaves it with the site.
2. **On when present, or on by default?** The proposal is "on when present", which makes the call longer for a site that uses everything and much clearer for one that doesn't.
3. **Is one `jobs` adapter enough for a site that sends events through Inngest and runs some jobs elsewhere?** Nobody does that today. The proposal is one adapter.
